Generic Embedded Linux Build Project
====================================

Purpose
-------
This document describes the capabilities provided by the project as a
reusable, hardware-neutral embedded Linux build template. Board, processor,
carrier, boot firmware, storage, kernel, and vendor BSP details belong in a
target configuration and are intentionally excluded from this specification.

Capability status
-----------------
The list uses these meanings:

- Implemented: provided by the current repository structure and build flow.
- Configurable: provided by a reusable mechanism and enabled or changed by
  project configuration.
- Platform-dependent: available only when the selected BSP, kernel, hardware,
  or storage layout supports it.
- Optional: present as a supported integration point but not required in every
  product image.

1. Project and Build Platform
-----------------------------
- Implemented: containerized Yocto/OpenEmbedded build environment.
- Implemented: Yocto, BitBake, and kas commands run through a Docker-based
  build container.
- Implemented: host workflow requires only the container runtime, curl, make,
  and ordinary shell utilities; Yocto and BitBake are supplied by the
  container.
- Implemented: kas version is pinned and downloaded or reused by the
  kas-container helper.
- Implemented: shared download and sstate caches reduce repeat-build time.
- Implemented: build, cache, and deployment directories are created on demand.
- Configurable: build directory, download directory, sstate directory,
  deployment directory, container image names, image target, SDK paths, and
  OTA package version.
- Implemented: target selection through a positional make argument, for
  example `make image <target>`.
- Implemented: target configuration supplies the Yocto MACHINE value and the
  build system validates that it can be derived.
- Implemented: interactive shell inside the configured kas/BitBake container.
- Configurable: Docker UID/GID mapping, SSH directory forwarding, cache
  locations, and build-container environment.
- Implemented: reproducible layer references when kas repository commits are
  pinned.

2. Target and Hardware Configuration
-------------------------------------
- Implemented: one kas configuration file per supported target profile.
- Implemented: shared kas configuration for common repositories, layers,
  local.conf values, distribution settings, and common capabilities.
- Configurable: target MACHINE, boot method, storage device, partition table,
  boot files, device trees, kernel configuration, firmware, and deployment
  behavior.
- Platform-dependent: removable media, soldered flash, eMMC, NVMe, network
  boot, USB boot, or other storage layouts.
- Platform-dependent: bootloader, boot firmware, secure boot, device-tree,
  kernel, hardware interfaces, and vendor BSP integration.
- Implemented: adding a target normally requires a new kas target file and any
  target-specific WIC, kernel, firmware, or deployment configuration.
- Configurable: product-specific kernel command-line additions and kernel
  configuration fragments through kas and BitBake variables.
- Optional: target-specific deployment hooks and board validation rules.

3. Image Composition and Storage
--------------------------------
- Implemented: custom image recipe based on a standard Yocto base image.
- Implemented: package groups for middleware, cloud/telemetry, debug, and SDK
  support.
- Implemented: WIC compressed image and WIC block-map output.
- Implemented: ext4 root filesystem output for OTA packaging.
- Implemented: image deployment into target- and timestamp-specific folders.
- Implemented: bmaptool flashing with block-device, image, and bmap checks.
- Configurable: image name, image features, installed packages, filesystem
  types, boot files, partition layout, labels, sizes, and mount points.
- Platform-dependent: BSP kernel and firmware integration.
- Optional: A/B layout with boot, rootfs-a, rootfs-b, and persistent-data
  partitions.
- Optional: persistent data or home partition preserved across rootfs updates.
- Implemented: first-boot initialization of a persistent user-data/home area
  when the selected layout provides one.
- Implemented: a rootfs expansion service that is safe for single-partition
  layouts and skips layouts containing later A/B or data partitions.
- Platform-dependent: boot firmware storage, boot-partition format, rootfs
  device naming, and firmware update process.

4. Operating System Foundation
------------------------------
- Implemented: systemd init and service management.
- Implemented: systemd-networkd based DHCP configuration for Ethernet and
  wireless interfaces.
- Implemented: wpa_supplicant integration for compatible wireless hardware.
- Implemented: BlueZ, rfkill, and wireless utilities when supported by the
  target hardware and BSP.
- Configurable: runtime wireless credentials and network interface files.
- Implemented: default non-root operator user with sudo access and locked
  default password.
- Configurable: operator password hash, authorized SSH keys, username, shell,
  and group membership.
- Implemented: optional SSH server and debug image features.
- Implemented: first-boot home-directory initialization from the image's
  skeleton directory when persistent storage is mounted over the home path.
- Platform-dependent: serial console and UART device availability.
- Optional: time synchronization, logging, auditing, certificates, crypto,
  and entropy services.

5. A/B OTA Updates
------------------
- Implemented: SWUpdate integration and `.swu` bundle generation.
- Implemented: compressed ext4 rootfs payload packaging.
- Implemented: configurable web-based SWUpdate service and command-line
  delivery through `swupdate-client`.
- Implemented: runtime detection of the active rootfs partition and selection
  of the inactive partition for an update.
- Platform-dependent: slot device naming, partition identifiers, bootloader,
  and boot configuration format.
- Implemented: partition-identifier-based rootfs selection for the next boot.
- Implemented: boot configuration backup and pending-update marker creation.
- Implemented: post-reboot boot-check service that records the active slot,
  confirms the requested partition, and restores the previous boot
  configuration after a failed slot boot.
- Implemented: restoration of boot configuration write protection after update
  edits where the platform mount supports remounting.
- Configurable: OTA web service port, package version, update timeout, retry
  count, hardware compatibility identifier, and post-update action.
- Implemented: timestamped or explicitly assigned OTA package versions.
- Optional: RSA-4096/SHA-256 signed OTA metadata and target-side hash/signature
  verification.
- Configurable: private signing key, installed public key, and secure
  production policy.
- Secure mode: requires configured signing material and rejects unsigned or
  unverifiable metadata when enabled.
- Optional: kernel, device-tree, bootloader, application, or data payloads may
  be added to the SWUpdate description when the selected platform defines
  their handlers and update policy.

6. Middleware, APIs, and Product Packages
-------------------------------------------
- Implemented: gRPC C++ runtime and development support.
- Implemented: Protocol Buffers runtime, compiler, lite runtime, and
  development support.
- Implemented: Python gRPC and Protocol Buffers bindings.
- Implemented: middleware package group with reusable runtime dependencies.
- Implemented: cloud and telemetry package group with MQTT/TLS dependencies.
- Implemented: debug and profiling package group.
- Implemented: SDK package group with development and test tooling.
- Configurable: package-group contents, feature flags, product applications,
  language runtimes, and service defaults.
- Optional: additional IPC, serialization, media, database, cloud, telemetry,
  or application frameworks through new package groups and recipes.

7. Hardware Interfaces and Diagnostics
---------------------------------------
- Implemented: I2C tools and Python SMBus bindings.
- Implemented: SPI tools and Python spidev bindings.
- Implemented: GPIO tools, libgpiod, and Python GPIO bindings.
- Implemented: UART/serial tools and Python serial support.
- Implemented: USB inspection utilities.
- Implemented: PCIe, NVMe, flash, SCSI, and storage diagnostics where recipes
  are available in the configured layers.
- Implemented: CAN utilities.
- Implemented: system inspection and diagnostics including hardware inventory,
  network inspection, memory/register access, CPU statistics, system
  statistics, tracing, video inspection, and input-event testing.
- Platform-dependent: availability and usefulness of each tool depends on the
  selected kernel, device tree, driver, and physical interface.
- Configurable: omit large diagnostic packages from production images while
  retaining them in development images.

8. SDK and Cross-Compilation
----------------------------
- Implemented: standard Yocto SDK generation through `make sdk`.
- Implemented: extensible SDK generation through `make esdk`.
- Implemented: SDK installer deployment into target- and timestamp-specific
  directories.
- Implemented: development headers, source packages, debug packages, and
  target development packages through SDK feature configuration.
- Implemented: gdbserver, perf, trace-cmd, valgrind, and ptest support where
  provided by the selected Yocto layers.
- Implemented: standard SDK Docker image generation.
- Implemented: extensible SDK Docker image generation.
- Implemented: automatic staging of SDK installers into Docker build contexts.
- Implemented: conditional ensure-sdk-image and ensure-esdk-image workflows.
- Implemented: eSDK workflow suitable for devtool-based recipe and source
  development.
- Configurable: SDK installation paths, image names, tags, toolchain contents,
  and target development package set.

9. Container Image Management
-----------------------------
- Implemented: KAS/Yocto build-container image generation.
- Implemented: SDK and eSDK development-container image generation.
- Configurable: image repository names, tags, kas version, SDK install path,
  and eSDK install path.
- Implemented: ensure-image targets that build missing Docker images.
- Implemented: Docker image cleanup target.
- Implemented: Dockerfiles and Makefiles that provide reproducible build
  inputs for the supported container images.

10. Artifact Deployment
-----------------------
- Implemented: deployment of compressed WIC images and bmap files.
- Implemented: deployment of standard SDK installers.
- Implemented: deployment of extensible SDK installers.
- Implemented: deployment of SWUpdate bundles.
- Implemented: target- and timestamp-specific deployment directories.
- Implemented: independent deployment targets that can be run after artifacts
  are built.
- Configurable: deployment root, naming scheme, retained artifact types, and
  release metadata.

11. Customization and Extensibility
------------------------------------
- Implemented: dedicated product layer for project-specific customization.
- Implemented: automatic BitBake recipe discovery under `recipes-*`
  directories.
- Implemented: package additions through the image recipe and package groups.
- Implemented: creation of new BitBake recipes and systemd services.
- Implemented: `.bbappend` customization for kernels, boot firmware, and BSP
  recipes without modifying upstream layers.
- Implemented: addition of new target profiles through kas configuration.
- Implemented: shared kas configuration for repositories, layers, machines,
  image settings, and local.conf values.
- Configurable: external layer revisions, branches, commits, licenses, and
  accepted license flags.
- Implemented: configurable kernel fragments, extlinux additions, user
  credentials, SSH keys, secure OTA keys, and product capability flags.
- Recommended: keep upstream layers immutable and place all product changes in
  the project layer.

12. Quality, Validation, and Utilities
---------------------------------------
- Implemented: Makefile syntax validation through `make lint`.
- Implemented: YAML parsing validation for common, target, and repository
  configuration files.
- Implemented: Docker and curl prerequisite checks through `make test`.
- Implemented: validation of every target configuration and its MACHINE value.
- Implemented: BitBake metadata and feature validation through `make validate`.
- Implemented: validation of middleware, cloud, debug, SDK, development,
  ptest, boot-file, secure-OTA, and OTA-script invariants.
- Implemented: target validation through `make check-board`.
- Implemented: Bash completion for Make targets and target names.
- Implemented: help output for build, Docker, deployment, cleanup, utility,
  validation, and target options.
- Implemented: rebuild workflow that clears the selected image recipe sstate
  before rebuilding.
- Implemented: clean workflows for build output, Docker images, caches, and
  deployment artifacts.
- Recommended: add target-specific smoke tests and hardware-in-the-loop tests
  for boot, networking, flashing, and OTA rollback.

13. Main Build Targets
----------------------
- `build` / `image`: build and deploy the selected image.
- `rebuild-image`: clear image recipe state, rebuild, and deploy the image.
- `sdk`: build and deploy the standard SDK installer.
- `esdk`: build and deploy the extensible SDK installer.
- `shell`: open an interactive build-container shell.
- `swu`: build and deploy an OTA bundle.
- `flash`: flash the newest validated image to a block device.
- `kas-image`: build the Yocto/KAS Docker image.
- `sdk-image`: build the SDK, its Docker image, and deploy the installer.
- `esdk-image`: build the eSDK, its Docker image, and deploy the installer.
- `deploy-images`, `deploy-sdk`, `deploy-esdk`, `deploy-swu`: deploy existing
  artifacts independently.
- `completion`: install Bash completion.
- `lint`, `test`, `validate`, `check-board`: run project checks.
- `clean`, `clean-build`, `clean-docker`, `clean-all`: remove generated data.
- `help`: display usage, targets, and supported target profiles.

14. Portability Rules
---------------------
- Do not put processor, board, carrier, vendor, or product names in this
  capability specification.
- Keep those details in target kas files, machine configuration, WIC files,
  kernel append files, and BSP integration files.
- Replace the project layer name with the new product layer name when reusing
  this template.
- Replace target files with the new hardware profiles while retaining the
  common kas configuration and Makefile contracts.
- Replace boot and storage handlers when the new platform does not use WIC,
  extlinux, systemd, or SWUpdate.
- Treat hardware tools, boot firmware, secure boot, OTA slot switching, and
  device naming as platform-dependent integrations rather than global facts.
