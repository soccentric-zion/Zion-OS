Generic Embedded Linux Project Layout
======================================

Purpose
-------
This document explains how the repository is organized, how a build moves
through the repository, where each kind of customization belongs, and how to
reuse the layout for another embedded Linux product or hardware family.

The layout separates four concerns:

1. Build orchestration: Makefile, helper scripts, and Docker build contexts.
2. Build composition: kas files, external layers, image recipes, package
   groups, services, kernels, boot files, and OTA metadata.
3. Target integration: one target configuration per machine or deployment
   profile.
4. Generated output: build state, downloads, shared state, deploy artifacts,
   and temporary files.

The product-layer directory is represented here as `meta/<product-layer>`.
When this layout is reused, replace the placeholder with the new product-layer
name and update its kas repository path and layer name.

1. Top-Level Layout
-------------------

    project-root/
    |
    +-- Makefile
    |   Main user-facing build interface.
    |
    +-- kas-container
    |   Convenience entry point for the maintained kas-container helper.
    |
    +-- scripts/
    |   Build helpers, completion, key generation, and maintenance scripts.
    |
    +-- docker/
    |   Docker build contexts for the Yocto, SDK, and eSDK environments.
    |
    +-- kas/
    |   Reproducible build composition and target selection.
    |
    +-- meta/
    |   Project-owned Yocto layer or layers.
    |
    +-- layers/
    |   kas-managed external layer checkouts; do not edit or track manually.
    |
    +-- feature/
    |   Capability and layout documentation.
    |
    +-- build/
    |   Generated Yocto build state; normally ignored by git.
    |
    +-- cache/
    |   Shared downloads and sstate cache; normally ignored by git.
    |
    +-- deploy/
    |   Release artifacts copied from the Yocto output directories.
    |
    +-- CLAUDE.md or project instructions
        Repository-specific operating rules and verified workflows.

The root repository should contain source, configuration, documentation, and
build orchestration. It should not contain generated Yocto work directories,
large downloads, sstate data, or manually managed copies of upstream layers.

2. Makefile Responsibilities
-----------------------------

The Makefile is the stable interface for developers and CI. It should hide
container details while exposing repeatable project operations.

Important variable groups:

- Container images:
  - KAS image name and tag.
  - SDK image name and tag.
  - eSDK image name and tag.
  - kas release version.
- Build selection:
  - image target.
  - target profile or board name.
  - derived kas configuration path.
  - derived Yocto MACHINE.
- Paths:
  - build directory.
  - download cache.
  - sstate cache.
  - deployment root.
  - SDK and eSDK installation paths.
- OTA:
  - package version.
  - signing key location.
  - secure production mode.

The Makefile provides these classes of target:

- Container targets: build or ensure the KAS, SDK, and eSDK images.
- Image targets: build, rebuild, deploy, and flash the target image.
- SDK targets: generate and deploy standard or extensible SDKs.
- OTA targets: package, sign, and deploy SWUpdate bundles.
- Shell target: enter the configured build container.
- Validation targets: lint, test, validate, and check-board.
- Cleanup targets: remove build state, caches, deployment artifacts, or Docker
  images.
- Utility targets: help and Bash completion.

Rules for extending the Makefile:

- Preserve existing public target names where possible.
- Add a variable when a value is expected to differ between projects.
- Pass board or target values explicitly into recursive make calls.
- Freeze timestamps and generated versions once per invocation.
- Keep destructive operations behind clearly named clean targets.
- Validate user-provided devices and paths before flashing or deleting.
- Keep all Yocto commands inside the kas container.

3. kas Directory
----------------

    kas/
    |
    +-- common.yaml
    |   Shared kas header, repository includes, distro, image target, common
    |   local.conf values, caches, image types, and common feature flags.
    |
    +-- boards/ or targets/
    |   One YAML file per supported target profile.
    |
    +-- repos/
        One YAML file per external repository or layer collection.

3.1 common.yaml

The common file is the single place for values shared by every target:

- kas configuration version.
- external repository includes.
- distro selection.
- default image target.
- init manager.
- image filesystem types.
- boot-file defaults shared by all targets.
- download and sstate cache locations.
- product capability flags.
- accepted license flags.
- common kernel or boot configuration variables.
- secure OTA defaults.

Do not put a target's storage device or boot partition in the common file when
those values differ between targets. Put them in the target file instead.

3.2 Target configuration files

A target file should contain only the values that identify or customize one
hardware or deployment profile:

- Yocto MACHINE.
- WKS file or other image layout.
- target-specific boot files.
- device-tree selection.
- kernel command-line additions.
- target-specific firmware.
- target-specific storage or deployment settings.
- target-specific license requirements.

A new target normally follows this process:

1. Copy the closest existing target YAML.
2. Change the MACHINE value.
3. Select or create the target WKS file.
4. Define boot files and device trees.
5. Add only the target-specific local.conf values.
6. Run `make check-board BOARD=<target>`.
7. Run `make lint`, `make test`, and `make validate`.
8. Build a small or complete image before declaring the target supported.

3.3 Repository files

Repository files define where external layers come from and which revision is
used. Each repository should have:

- URL.
- protocol.
- branch when needed for discovery.
- immutable commit pin for reproducibility.
- kas checkout path.
- layer paths exposed by the repository.

External layer contents belong under kas-managed `layers/` and must not be
patched directly. Use a project-layer recipe, `.bbappend`, configuration
fragment, or a fork intentionally managed as a separate repository.

4. Project Yocto Layer
----------------------

The project layer contains product-owned behavior and is the main portability
boundary between the generic build and a product implementation.

Current conceptual structure:

    meta/<product-layer>/
    |
    +-- conf/
    |   Layer configuration and layer priority.
    |
    +-- recipes-core/
    |   Image recipes, package groups, users, and core services.
    |
    +-- recipes-connectivity/
    |   Network, wireless, Bluetooth, and connectivity defaults.
    |
    +-- recipes-kernel/
    |   Kernel append files and configuration fragments.
    |
    +-- recipes-bsp/
    |   Bootloader, firmware, device-tree, and BSP append files.
    |
    +-- recipes-swupdate/
    |   Target runtime OTA configuration and boot-check service.
    |
    +-- recipes-support/
    |   First-boot, expansion, storage, and utility services.
    |
    +-- swupdate/
    |   Build-time OTA description and package scripts.
    |
    +-- wic/
        WIC partition layout files.

4.1 conf/layer.conf

This file declares the layer to BitBake. It normally sets:

- Layer collection name.
- Layer priority.
- Recipe search paths.
- Compatibility with the supported Yocto release.

Keep layer.conf small. Feature logic belongs in recipes, package groups, image
recipes, or configuration files.

4.2 Image recipes

The base image recipe defines the common operating system composition:

- Base Yocto image inheritance.
- Package groups.
- OTA runtime.
- Connectivity.
- Users and sudo policy.
- Hardware tools.
- Development and debug features.
- First-boot services.
- Secure key installation.

Shared image content should be placed in an include file when several image
variants use it. Product or vertical image variants should require the base
image and append only their additional packages.

A typical image composition pattern is:

    require recipes-core/images/base-image.bb
    require recipes-core/images/base-image-common.inc
    IMAGE_INSTALL:append = " product-packagegroup"

Avoid putting target storage assumptions directly in the image recipe. Use
MACHINE configuration, WKS files, or target-specific overrides.

4.3 Package groups

Package groups provide named capability bundles instead of placing a long
unstructured package list in every image. Typical groups include:

- middleware.
- cloud and telemetry.
- debug and profiling.
- SDK and development.
- hardware diagnostics.
- production runtime.

A package group should describe a capability boundary and should keep runtime
requirements separate from build-time development recommendations.

4.4 Connectivity recipes

Connectivity recipes install files and services such as:

- systemd-networkd network files.
- wpa_supplicant configuration.
- systemd presets.
- resolver integration.
- Bluetooth defaults.

Credentials should not be committed as shared secrets. Use deployment or
machine configuration, provisioning, secure storage, or runtime enrollment.

4.5 Kernel and BSP append files

Use `.bbappend` files to customize upstream recipes without changing the
upstream layer. Appropriate uses include:

- kernel configuration fragments.
- device-tree additions.
- bootloader configuration.
- firmware deployment.
- extlinux or boot-file preparation.
- target-specific patches.

Keep generic kernel hardening in a reusable fragment. Keep vendor secure-boot
signing and target release steps in the product release process when they are
not part of the normal image build.

4.6 Support services

Support recipes package small, focused system services:

- first-boot home initialization.
- rootfs expansion.
- storage preparation.
- boot confirmation.
- health checks.
- diagnostics.

Each service should provide its systemd unit, install files through a recipe,
state its runtime dependencies, and define whether it is enabled by default.

5. WIC and Storage Layouts
--------------------------

WIC files describe the image partition table and mount points. A layout may
contain:

- boot partition.
- root filesystem.
- inactive A/B root filesystem.
- persistent data or home partition.
- recovery partition.
- vendor or firmware partition.

A WIC file must agree with all of the following:

- IMAGE_BOOT_FILES.
- kernel and device-tree deployment names.
- mount points in `/etc/fstab` or systemd mount configuration.
- OTA slot detection logic.
- bootloader rootfs selection.
- first-boot expansion behavior.
- flashing and deployment documentation.

For A/B layouts, document clearly:

- which partition is initially active.
- how the inactive partition is identified.
- how the boot configuration selects a slot.
- how pending updates are recorded.
- how a failed boot is detected.
- how rollback restores the previous selection.
- which data partitions survive an update.

Never use a generic rootfs expansion service on a fixed A/B layout unless it
first detects and refuses to resize a partition that has another partition
behind it.

6. SWUpdate Layout
------------------

There are two related OTA surfaces and they must remain synchronized:

    meta/<product-layer>/swupdate/
    |   Build-time files copied into manually generated `.swu` bundles.
    |
    +-- recipes-swupdate/.../files/
        Files installed into the target root filesystem.

The pre-install and post-install scripts used by both surfaces must have the
same behavior. A validation check should compare them or use one generated
source to avoid drift.

The OTA flow is:

1. Build an ext4 root filesystem.
2. Compress the rootfs for the SWUpdate bundle.
3. Identify the active rootfs device at installation time.
4. Select the inactive slot using the target storage naming rules.
5. Write the image through a stable update-device reference.
6. Resolve the target partition identifier.
7. Back up the existing boot configuration.
8. Change the boot configuration to select the new slot.
9. Write a pending-update marker.
10. Reboot or wait for the configured post-update action.
11. Confirm the active slot after reboot.
12. Remove the marker on success or restore the backup on failure.

For signed OTA mode:

- generate a private/public key pair outside source control.
- keep the private key in a protected release environment.
- install only the public key into the target image.
- enable SWUpdate signature and hash verification.
- sign the metadata with the expected algorithm.
- fail image or package creation when secure mode lacks required keys.
- test that unsigned and tampered bundles are rejected.

7. Docker Layout
----------------

    docker/
    |
    +-- yocto/
    |   Build context for the kas/Yocto container.
    |
    +-- sdk/
    |   Build context for a container containing the generated standard SDK.
    |
    +-- esdk/
        Build context for a container containing the generated extensible SDK.

Each context should have:

- Dockerfile.
- Makefile.
- stable base image choice.
- build arguments for version and install path.
- clear input artifact expectations.
- no dependency on a developer's untracked local files.

The root Makefile should stage generated SDK installers into these contexts,
invoke the context Makefile, and deploy the resulting installer artifacts.

8. Generated Directories
-------------------------

8.1 build/

The Yocto build directory contains configuration, task state, workspaces,
package data, logs, deploy output, and BitBake services. It is generated and
can be deleted with the build cleanup target.

Important subdirectories include:

- `conf/`: generated local.conf and bblayers.conf.
- `tmp/`: work, sysroots, stamps, logs, and deploy output.
- `cache/`: BitBake persistent metadata and service state.

Do not edit generated configuration as a permanent fix. Change kas or layer
configuration instead.

8.2 cache/

The cache directory contains shared source downloads and sstate artifacts.
It is safe to preserve between builds and normally excluded from version
control. It can be moved to a larger disk through Makefile variables.

8.3 deploy/

The deploy directory contains release-ready copies of artifacts, organized by
artifact class and target snapshot:

    deploy/
    |
    +-- images/<target>_<timestamp>/
    +-- sdk/<target>_<timestamp>/
    +-- esdk/<target>_<timestamp>/
    +-- swu/<target>_<timestamp>/

The original Yocto deploy directory remains under `build/tmp/deploy`. The
root-level deploy directory is the curated handoff area.

9. Build Flow
-------------

The normal image flow is:

    developer command
          |
          v
    Makefile parses target and derives target config
          |
          v
    ensure Docker image and kas-container helper
          |
          v
    create build/cache directories
          |
          v
    validate target and derive MACHINE
          |
          v
    run kas build inside Docker
          |
          v
    BitBake parses layers and builds the image
          |
          v
    WIC/ext4 artifacts appear in build/tmp/deploy/images/<MACHINE>
          |
          v
    deploy-images copies release artifacts to deploy/images/<target>_<time>

The SDK flow runs `populate_sdk` or `populate_sdk_ext`, stages the installer,
builds the corresponding development container, and deploys the installer.

The OTA flow consumes a previously built ext4 rootfs, packages it with the
SWUpdate description and scripts, optionally signs it, and deploys the bundle.

The flash flow validates `DEVICE`, finds the newest WIC and bmap pair, and
invokes bmaptool. It should be treated as a destructive operation.

10. How to Replace This Layout for Another Project
---------------------------------------------------

10.1 Rename the product layer

1. Rename `meta/<old-product-layer>` to `meta/<new-product-layer>`.
2. Update the kas repository path in the product-layer repository file.
3. Update the layer collection name in layer.conf.
4. Update all recipe paths and references if the layer name appears in them.
5. Search for the old name across Makefile, kas, Docker, scripts, and docs.
6. Confirm no generated `layers/` checkout is being edited accidentally.

10.2 Define target profiles

1. List every supported hardware or deployment profile.
2. Create one kas target file for each profile.
3. Set MACHINE and the target WKS or image layout.
4. Define boot files and device trees.
5. Define storage and firmware behavior.
6. Add target-specific license flags only where required.
7. Run check-board for every profile.

10.3 Adapt storage and boot

1. Decide whether the product uses one rootfs, A/B rootfs, recovery, or a
   separate data partition.
2. Write the WIC file for the selected storage medium.
3. Ensure IMAGE_BOOT_FILES matches the WIC boot partition.
4. Implement bootloader slot selection if A/B OTA is required.
5. Update OTA device discovery for the new device naming scheme.
6. Test first boot, reboot, update, failed update, and rollback on hardware.

10.4 Adapt the image

1. Replace the image summary and product package groups.
2. Keep generic runtime packages in a common include file.
3. Add product applications as separate recipes.
4. Add product services with systemd units and explicit dependencies.
5. Move secrets and deployment credentials out of the source tree.
6. Create production and development image variants if their package sets
   differ substantially.

10.5 Adapt connectivity and hardware tools

1. Confirm the kernel drivers and device-tree nodes for each interface.
2. Keep interface configuration in target or product configuration.
3. Remove packages for hardware that cannot exist on the new target.
4. Keep diagnostic packages optional for production images.
5. Add smoke checks for network, storage, serial, GPIO, I2C, SPI, USB, and CAN
   only when those interfaces are part of the product contract.

10.6 Adapt OTA security

1. Choose the signing and verification policy.
2. Add or retain SWUpdate Kconfig verification support.
3. Provision the public key through a controlled image build.
4. Keep private keys in CI or a release signing service.
5. Define downgrade, compatibility, rollback, and recovery policy.
6. Test unsigned, tampered, incompatible, interrupted, and failed-boot updates.

10.7 Adapt CI and release checks

At minimum, CI should run:

- `make lint`.
- `make test`.
- `make validate`.
- `make check-board` for every target.
- shell syntax checks.
- BitBake parse or image build checks.
- artifact existence and naming checks.
- target hardware smoke tests.
- OTA update and rollback tests for production-capable targets.

11. Portability Checklist
-------------------------

Before declaring the layout reusable, confirm:

- No product or processor name is required by the generic feature document.
- Every target-specific value is isolated in a target configuration.
- External layers are pinned to immutable revisions.
- Upstream layers are not patched in place.
- The product layer owns all custom recipes and append files.
- WIC, boot files, kernel deployment, and bootloader configuration agree.
- OTA scripts support the selected storage device names.
- OTA rollback state is created and consumed by the same update flow.
- Secure OTA mode fails closed when keys or verification support are absent.
- Generated directories are ignored and removable.
- Deployment artifacts are separated from build state.
- Documentation describes the replacement steps for the next project.
- A full build and hardware validation have been completed for each claimed
  target profile.
